# AGENTS.md

Shared instructions for human and AI contributors working in this repository.

## What This Repo Is

Family Chat Desktop is a native Rust Matrix client for macOS, Linux and Windows, focused on:

- being the best way to use Family Chat (`safechat.family`), including sign-in with a code from a parent
- standards-compliant Matrix through the matrix-rust-sdk, with end-to-end encryption by default, for any homeserver
- a GPUI desktop window and a ratatui terminal UI that share all non-visual logic
- security and privacy first: secrets only in the OS keychain, encrypted local stores, no third-party services

It is built in the same style as Zmail (unicornops/zmail): the same workspace shape, toolchain, lint and dependency policy, CI and release flow, ADR habit and agent instructions.

It is alpha software. Phase 0 (the scaffold), Phase 1 (secrets and the local store), Phase 2 (the local homeserver harness), Phase 3 (the Matrix session core), Phase 4 (the sign-in core), Phase 5 (the GUI shell and sign-in screens), Phase 6 (rooms and the timeline in the GUI), Phase 7 (messaging actions and the composer), Phase 8 (end-to-end encryption), Phase 9 (notifications, single instance and sign-in links), Phase 10 (the terminal UI: sign-in and reading) and Phase 14 (sign-in in the browser and with a QR code for servers that offer them) are in place: a Family Chat window that opens the profile (with the keychain and lost-key screens), signs in by code (pasted link, pasted or dropped QR image) or password, shows the account's rooms (filters, badges, invitations, members) and timelines (sanitised rich text, media through authenticated media, links that ask first) with its sync state, and writes in them through `familychat-actions` (Markdown and mentions, replies, edits, reactions, deletions, files checked against the server's limit and without their location, the send queue with offline retry, drafts, typing and read receipts, "Chat is paused" with a read-only composer during a curfew), end-to-end encryption people can live with ("Confirm it's you" after every sign-in, by emoji, a QR code for a phone, or the recovery key, skippable with a warning; cross-signing made with no password through MSC3967 or with the password when a server asks; recovery shown once; verification requests, the devices, identity-change banners, reasons for unreadable messages, Send anyway, and room key export and import; Element X's defaults, ADR 0009), a terminal UI in Zmail's style that opens the same profile, signs in by pasted link or password and reads the same rooms and timelines (every server string filtered for the terminal), the keychain and the encrypted app store behind `familychat accounts`, real homeservers to test against, Matrix sessions that restore, sync and stream rooms and timelines to any frontend through `SessionApi`, every Family Chat and password sign-in rule behind `SigninApi`, the screenshot fixtures and view tests every later GUI phase uses, the terminal UI's fixture views and snapshots, system notifications for the rooms you aren't looking at (coalesced per room, capped, with the text hidden on request) with the unread total in the window's title, the single-instance hand-off: a second `familychat LINK` or `familychat open-link` forwards its sign-in link over a user-only socket or pipe to the running window, which asks "Sign in as …?" before anything is redeemed, and, for servers that offer them (never Family Chat's Palpo today), OAuth 2.0 (MSC3861) and single sign-on in the system's browser after a confirmation with the full address, and QR code sign-in (MSC4108) both ways in the window (ADR 0010). Writing and encryption from the terminal are Phase 11; registering `familychat://` with the OS is Phase 12. Each later phase is a GitHub issue (phase N is issue #N+1, tracked in #16).

## Workspace Overview

- `crates/familychat-app`: the `familychat` binary: CLI (`familychat` opens the window, `familychat LINK` opens it with a sign-in link, `familychat open-link` reads the link from standard input, `familychat tui`, `familychat accounts`, `familychat start-over`, `familychat --version`, `familychat help`), wiring, and `build.rs` (the Zed pin read from `Cargo.lock`, the Windows version resource). Every command that uses the profile takes its lock first, then starts logging, then opens the keychain and the store. The window that holds the lock listens on the profile's `familychat-instance` endpoint and hands what arrives (checked with the sign-in's `LoginLink::parse`) to the window's request channel; a launch that finds the profile locked forwards its link, or "come forward", and exits (never logging: it has no lock), and says "already open" when nothing listens (the terminal UI). Links given on the command line are checked before anything else and never echoed. The window's `startup::LiveStartup` (the `StartupApi`) opens the profile on the background runtime (the keychain and the store in a blocking task, then `AccountManager::restore_all`, `LiveSession` and `LiveSignin` over `ReqwestTransport`), keeps a not-ready profile (and its lock) for Try again and Start over, and the window's close stops the syncs. The terminal UI is its `tui` feature, on by default: `familychat tui [--bell] [--ascii] [--no-mouse]` (and `FAMILYCHAT_TUI_COPY_COMMAND`) takes the lock, then runs `familychat-tui` over the same `LiveStartup`, and stops the syncs when it ends. `ui-fixture` (off by default, never in a release) adds `familychat launch-ui-fixture VIEW [dark|light]` (`--list` names the views) over `familychat-test-support`'s fixtures, and `familychat launch-tui-fixture VIEW` (`--list`; `src/tui_fixture.rs`) over `familychat-tui`'s `fixture_views` (it turns on that crate's `fixture-views` feature). `tests/live_tui_signin.rs` is the terminal UI's live sign-in test
- `crates/familychat-actions`: what a person does in a room (ADR 0012), shared by both frontends, with no GPUI, ratatui or matrix-sdk dependency: `Actions` (one per account, over `SessionApi`) returns `ActionTask`s (futures for any executor) and reports `ActionEvent`s (done, refused, failed, a room made, a draft read; `message()` is the sentence) to a plain callback (`Actions::channel` puts them on a channel): send (with `SendTarget::{New, Reply, Edit}`), reactions, redactions, `mark_read`, typing, `send_file` and `file_allowed`/`check_file`, invitations, leaving, `create_room` and `create_direct_chat` (encrypted unless the well-known says `io.element.e2ee.default: false`, `encrypt_new_room`; `RoomCreated` says whether), `send_anyway` (a message the encryption stopped, ADR 0009), drafts. Every write is refused with `Refusal::Paused` while the account is suspended. `markdown` (ruma's Markdown, mentions as `matrix.to` links, the HTML through the security crate's sanitiser), `mentions` (the `@` query, suggestions from the members, completion), `files` (`FileSource`, the size check before reading, `image_metadata` cleaning, MIME types, size wording), `ComposerState` and `TypingNotices`. Offline tests run over the fixture session (`src/tests.rs`); live tests are `tests/live_actions.rs` (round trips between two members, offline sends with the front end stopped, the paused composer, the upload limit from the access log, a photo's bytes without GPS, new direct chats encrypted)
- `crates/familychat-ui`: the GPUI frontend: `ShellView` (the window root: Zmail's title bar and window frame, the theme following the OS appearance, the command palette, toasts; the requests from outside the window (`RequestInbox`: forwarded links, macOS's `on_open_urls`), which start a sign-in on the sign-in screen or over the rooms and never interrupt one in use; the session's notifications, in bursts, and the unread total in the window's title) over a `StartupApi`; `notifications` (posting `familychat-notify`'s notifications through GPUI's system notifications with opaque tags, a click opening the room through `RoomsView::open_notified_room`, and the notification settings dialog; `signed_in` (the sync banner over the rooms, and the title bar's sync indicator; it holds the account's `EncryptionView` and hands it the verification requests); `encryption` (`EncryptionView`, ADR 0009: "Confirm it's you" in the rooms' place (another device, the recovery key, skipping after a warning), the page asking for the password the server wants, the banners (not confirmed, set-up failed, recovery offered), and the dialogs: the verification (waiting, incoming, the QR code drawn dark on white, the seven emoji, scanned, done or why it stopped), recovery with the key shown once (Copy, Save to a file, Done once kept), the devices with Verify and Sign out (the password when the server asks), room key export (the passphrase twice) and import; `EncryptionLaunch` for the fixtures); `rooms` (`RoomsView`: the room list (Zmail's `uniform_list` rows, the filters, unread and mention badges, invitations answered from the row or the room), the room header with its encryption badge and the not-encrypted banner (held back for a room this window just made encrypted), the open room's identity warnings (OK, Withdraw verification), the member list, the open-link dialog, the narrow (below 760 px: the list or the room) and wide (from 1180 px: the members beside the timeline) layouts; ## Repo Expectations For Agents

- Keep the UI off the network: the frontends draw view models from local state and never talk to a server themselves. Never block the UI thread on network, disk, crypto or decoding.
- Preserve the crate boundaries in ADR 0001: `familychat-ui` and `familychat-tui` never depend on matrix-sdk, matrix-sdk-ui or each other's toolkit, and `familychat-core` exposes no matrix-sdk types (it has no matrix-sdk dependency at all), and `familychat-actions` depends on neither the SDK nor a frontend's toolkit. `familychat-signin` depends on the session crate, so the frontends reach sign-in only through `familychat-core`'s `SigninApi`. `scripts/check-dependency-boundaries.sh` checks this in CI.
- Sign-in rules live only in `familychat-signin` (ADR 0006); a frontend draws `SigninStep`s and sends `SigninAnswer`s and never decides a rule. The window sends `SigninAnswer::Continue` only from the confirmation dialog while the step is `Confirm` (a view test drives the fixture sign-in to prove no code is redeemed without it); a QR image is decoded locally and its text handed to the sign-in as `SigninStart::Link`, never shown or kept. Every server name goes through `ServerName::parse`, every credential only to a `CheckedHomeserver`, every sign-in request through its `Transport` (never matrix-sdk), and nothing retries a login on its own. A change to a rule changes family-chat's `docs/client-login-links.md` too, and ADR 0006's table. A browser opens only after the person's Continue on the dialog that shows the whole address (`ConfirmBrowser`), once, and a frontend never shows or logs a `BrowserUrl`; for a Family Chat homeserver every OAuth and QR code address is under the allowlist (ADR 0010).
- Every Matrix future runs on `BackgroundRuntime`; results come back through runtime-agnostic channels that GPUI tasks await (`cx.spawn`) or the terminal UI polls (ADR 0005). Frontends keep their own lists, apply `ListDiff` batches and coalesce bursts into one redraw.
- matrix-sdk, matrix-sdk-ui, matrix-sdk-base (for the attachment decryptor), matrix-sdk-store-encryption and ruma are pinned exactly and move together; keep their features minimal (ADR 0005).
- A message's HTML never reaches a frontend: the session turns `formatted_body` into `RichText` through `familychat-security::matrix_html` (ADR 0007), and frontends draw the tree, never markup, and never the sender's colours. A frontend never fetches or decodes media: it asks `SessionApi::image` (authenticated media only, decoded within `familychat-security::images`' limits, never SVG) and gets RGBA pixels. A frontend opens a link only through `links::classify`: Matrix links in the app, anything else after a dialog that shows the whole address, never without asking. Files are saved only where the person chose, under the session's safe name, and never opened.
- In the terminal UI, every string from a server (names, topics, bodies, link text and addresses, file names, reactions, the sign-in's and the session's sentences) goes through `familychat_security::terminal::sanitize` (or `sanitize_line`) before it is drawn, and the only escape sequences written are ratatui's, the bell and OSC 52 for the person's own copy (ADR 0008). The terminal sends `SigninAnswer::Continue` only for `y` on the confirmation.
- A suspended account (`M_USER_SUSPENDED`) is `SyncState::Suspended`, never a generic error and never a fast retry loop; don't build anything that assumes either outcome of family-chat decision 11 (whether reads work while suspended). While suspended nothing is sent: `familychat-actions` refuses every write with `Refusal::Paused` and the composer is read-only.
- A frontend changes a room only through `familychat-actions` (ADR 0012), never by building `RoomRequest`s itself: the Markdown, the sanitiser's check on what is sent, the upload limit (checked before a file is read or uploaded), taking a picture's location out, and the encryption default for new rooms are its rules.
- Secrets live only in the OS keychain, through `familychat-security`'s `Keychain`: never in a file, the store, an environment variable or a log, and there is no plaintext fallback when the keychain is locked or missing (ADR 0003). Hold them in `Secret<T>` (or `Passphrase`), and give any new secret-bearing type a `Debug` that prints `[redacted]`.
- Encryption follows ADR 0009: all crypto is the SDK's, in `familychat-session`; a frontend draws `EncryptionStatus` and `VerificationFlow` steps and answers, and never sees a matrix-sdk type. A password answering UIA, a recovery key and a key file's passphrase travel as `SecretText`/`Secret`, are used for one request and wiped, and are never stored or logged; the recovery key is shown once. The encryption defaults (Element X's, with the one recorded difference) change only with that ADR.
- Never log tokens, passwords, keys, message bodies or query strings. Wrap private values in `Redacted`; the log scrubber is a second line of defence, not the first.
- In the app store, encrypt anything that identifies a person, a server or a room with the `StoreCipher` (keyed hashes for lookups); only non-identifying preferences are plaintext. `rusqlite` stays on the line `matrix-sdk-sqlite` uses (`libsqlite3-sys` links SQLite once per build) and moves only with the Matrix crates; no SQLCipher.
- Take the profile lock before touching the keychain or the store: one process per profile. A second launch never opens the profile: it forwards to the window over `familychat-instance` (ADR 0013) and exits. A forwarded link is a sign-in like any other: the window starts `SigninStart::Link` with it, and the confirmation always comes first. Never put a link in an error, a log line or a file, and prefer `familychat open-link` (standard input) to a link in `argv`.
- `unsafe` is forbidden everywhere except `crates/familychat-instance/src/windows_security.rs` (the Win32 security calls for the pipe's DACL), where each block is justified; don't add another without an ADR.
- Notifications go only to the local OS notification centre, never anywhere else; nothing for the room in front of the person, and "New message" when the person hides content.
- Tests never touch the developer's real keychain: use `MemoryKeychain`. Real-keychain tests are `#[ignore]`d, use a test-only service id, and run in CI's build job on each OS.
- Keep security and privacy defaults strict. User message content is never sent to a third-party hosted service: the app talks only to the account's homeserver. No analytics, crash reporting or remote logging, no link previews, no remote content beyond the homeserver.
- Nothing may be copied from the Element forks (AGPL-3.0) into this GPL-3.0-only codebase. Code copied from Zmail keeps a note saying so; record ported files and bundled assets in `about.toml`.
- Pin upstream inputs tightly and move them deliberately. Record each significant decision as an ADR in `docs/adr/`.
- Release packaging ships platform archives (Linux, macOS, Windows) with `LICENSE`, `THIRD_PARTY.html` and the bundled assets' licences. Native installers (`.deb`, DMG, MSI), signing and the `familychat://` scheme registration are Phase 12: do not describe any of them as done until they are.

Core verification:

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
```

Store and security tests run in the workspace tests on every OS. The real-keychain tests are ignored there; run them on a desktop session with `cargo test -p familychat-security -- --ignored real_keychain`, or on headless Linux against a throwaway Secret Service with `scripts/keychain-session.sh cargo test -p familychat-security -- --ignored real_keychain` (needs `dbus` and `gnome-keyring`; your own keyrings are never seen). CI's build job runs them on each OS, and `familychat accounts` twice through the platform keychain.

UI view tests use GPUI's test platform (`#[gpui::test]` with `TestAppContext`, from the `test-support` feature in `familychat-ui`'s dev-dependencies). They run headless with no display server; on Linux they only need the build packages below. A test that waits on another thread (the Tokio runtime, or the fixture sign-in's flow threads) calls `cx.executor().allow_parking()` first. They draw over `familychat-test-support`'s fixtures (`src/view_tests.rs` opens the window on a `FixtureStartup`). Every control is named through `AccessibleExt::accessible` and every pointer target marks itself with `HitTargetExt::hit_target`; `view_tests/a11y.rs` and `view_tests/hit_targets.rs` check every screen for empty names and targets under 24 px, and `styles::contrast` checks both bundled themes against WCAG AA. A new screen adds a fixture view, a screenshot matrix entry in dark and light, and both checks. `view_tests/rooms.rs` drives the rooms over the fixture family (filters, commands, invitations, links, pictures, saving), `view_tests/composer.rs` the composer and the message actions (Enter and Shift+Enter, mentions, replies and edits, files and the upload limit, the paused composer, reactions, deleting and leaving, drafts, typing and receipts, checked in `SessionRecord::requests`), `view_tests/encryption.rs` the encryption screens and dialogs (confirming and skipping, the recovery key, the password page, emoji and incoming verification with the QR code, recovery shown once and saved, the devices and signing out, export and import, identity warnings, Send anyway, each with its names and 24 px targets), and `view_tests/perf.rs` checks that the 1,000-room, 10,000-event fixture scrolls laying out only the rows on screen; its ignored `performance_budgets` is the recorded benchmark (ADR 0007): `cargo test --release -p familychat-ui --lib performance_budgets -- --ignored --nocapture` (`FAMILYCHAT_PERF_REPORT=<dir>` writes the table).

UI screenshots (what CI's UI Screenshots job runs on pull requests that touch the UI, uploading the `ui-screenshots` artefact; needs Xvfb, openbox, xdotool, ImageMagick and `mesa-vulkan-drivers`; look at the PNGs before calling a UI change done):

```bash
cargo build -p familychat-app --release --locked --features ui-fixture
target/release/familychat launch-ui-fixture --list          # the fixture views
target/release/familychat launch-ui-fixture confirm light   # one view, by hand

```

The matrix in `scripts/capture-ui-screenshots.sh` covers every fixture view in dark and light (a test in `familychat-app` checks it against the views), the rooms at 560 px and 1600 px wide too. The capture job installs Noto Color Emoji and DejaVu Sans Mono, so reactions and code draw as on a desktop. `cargo test -p familychat-app --features ui-fixture` runs the fixture's own tests; CI's quality job runs it. `view_tests/notifications.rs` posts the session's notifications on the test platform and clicks them, and `view_tests/forwarded_links.rs` drives forwarded links through the request channel.

Terminal UI (ADR 0008): `cargo test -p familychat-tui` runs the snapshots (every fixture view at 80x24 and 160x48, with `NO_COLOR` and ASCII; rewrite with `FAMILYCHAT_UPDATE_SNAPSHOTS=1` and review the diff), the hostile-text test and the key, mouse, paste, link and file tests over the fixtures, with a fixed clock in UTC. A new screen adds a fixture view to `familychat_tui::fixture_views` and its snapshot test; tests in `familychat-tui` and `familychat-app` fail otherwise. `cargo run -p familychat-app --features ui-fixture -- launch-tui-fixture VIEW` opens a view in a real terminal. A change to the terminal UI records the manual check in a real terminal on each OS (ADR 0008, "Consequences").

Live homeserver harness (ADR 0004; needs Docker with Compose, `curl`, `jq` and `openssl`):

```bash
scripts/homeserver-harness.sh up       # Palpo (Family Chat's image) + Postgres, Synapse, the TLS front end; bootstraps the admin bot
cargo test -p familychat-test-support --test live_homeserver_harness -- --ignored
cargo test -p familychat-session --test live_session -- --ignored   # the Matrix session against Palpo and Synapse (messages, an image and a notification from another user included)
cargo test -p familychat-signin --test live_signin -- --ignored     # the sign-in against Palpo and Synapse, checked in the access log
cargo test -p familychat-signin --test live_oauth -- --ignored --nocapture   # OAuth on Synapse with MAS (refresh, revocation), QR code sign-in both ways, none on Palpo
cargo test -p familychat-actions --test live_actions -- --ignored   # sending, replies, edits, reactions, deletions, offline sends, the paused composer, files and photos on Palpo
cargo test -p familychat-session --test live_encryption -- --ignored --nocapture   # emoji verification and history, recovery on a new device, a code-only account's cross-signing (the outcome printed), room key export and import
cargo test -p familychat-app --test live_tui_signin -- --ignored    # the terminal UI's sign-in by pasted code and by password
scripts/homeserver-harness.sh env      # the FAMILYCHAT_HARNESS_* settings the tests read
scripts/homeserver-harness.sh mint-token alice   # a single-use m.login.token for @alice:hs1.familychat.test
scripts/homeserver-harness.sh create-mas-user bob bob-password   # a MAS user on synapse-mas.familychat.test
scripts/homeserver-harness.sh stop-edge          # the front end down (every host unreachable), and start-edge to bring it back
scripts/homeserver-harness.sh down
```

The front end serves `hs1.familychat.test` (a Family Chat family's edge proxy, Palpo), `smith.test` (a custom domain whose well-known delegates to hs1), `evil.familychat.example` (a homeserver outside the allowlist), `redirect.familychat.test` (allowlisted, but its `/login` answers 307 to the evil host), `synapse.test`, and `synapse-mas.familychat.test` (Synapse delegating sign-in to MAS, allowlisted, with the MSC4108 rendezvous) and `mas.familychat.test` (MAS, its issuer) on `127.0.0.1:18443`, logging every request as `host method path status` to `target/homeserver-harness/edge-logs/access.log` (`HomeserverHarness::access_log`), with a CA made on every `up` (`target/homeserver-harness/ca.pem`); Palpo's admin API is on `127.0.0.1:18008` and Synapse's on `127.0.0.1:18009`. Synapse issues refresh tokens with 20-second access tokens, so the session tests see rotation (`HomeserverHarness::new_synapse_user`); MAS's access tokens last a minute (`HomeserverHarness::new_mas_user`). Nothing on the machine trusts the CA: only `familychat-test-support`'s client does. Live tests are `#[ignore]` and need the harness up first; CI's quality job runs them with `-- --ignored`, with Docker Hub logins from the optional `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN` secrets. Create members through the admin API (`HomeserverHarness::new_user`), not registration: Palpo allows a burst of only three registrations per peer, and the whole harness is one peer. `scripts/check-release-features.sh` (CI and the release workflow) fails if a release build of `familychat-app` could include `familychat-test-support`, any `test-harness` feature or a Family Chat crate's `staging` feature (`familychat-signin`'s, which allows `*.familychat.dev`); never make the app depend on them. Sign-in tests build `familychat-signin` with `test-harness` (its `*.familychat.test` allowlist) and hand `ReqwestTransport::with_builder` the harness's `edge_client_builder`, whose CA and resolver it keeps while forcing its own no-redirect, no-retry settings. Session tests get the harness's HTTP client through `SessionConfig::with_http_client`; the session crate itself never trusts a test CA.

The keymaps are `crates/familychat-ui/keymaps/default.json` (and `macos.json`, the macOS window conventions). Every command is a row of `familychat_core::commands::COMMANDS` and a `familychat::<id>` GPUI action bound to exactly the table's keys; tests fail when a command lacks a window or terminal key, when the keymap and the table disagree, or when an action is in neither. `FAMILYCHAT_WINDOW_DECORATIONS=server|client` overrides the Linux title-bar choice (client-side everywhere but KDE).

GPUI pin:

- GPUI is a git dependency pinned to a Zed stable release tag (`tag = "vX.Y.Z"` on the `gpui` and `gpui_platform` lines of `Cargo.toml`), not the crates.io `gpui` crate. Keep both lines on the same tag, and `rust-toolchain.toml` on the toolchain Zed pins at that tag.
- The weekly `zed-upstream` workflow (`scripts/bump-zed-gpui.sh`) opens a `chore(deps): bump Zed GPUI to vX.Y.Z` pull request when Zed ships a newer stable release; see `docs/upstream/zed.md` for manual bumps and the mirrored `[patch.crates-io]` entries.
- Start the app with `gpui_platform::application()`. Do not use `Application::new_inaccessible`, which disables AccessKit screen-reader support.

Releases:

- release-please (`.github/workflows/release-please.yml`) keeps a release pull request open from the Conventional Commits on `main`; `scripts/render-release-pr.sh` adds the commits outside `crates/familychat-app` that release-please does not count. - Release pull requests and Zed bump pull requests are opened with `RELEASE_PLEASE_TOKEN` when that secret exists, otherwise with `GITHUB_TOKEN`, whose pull requests do not start CI on their own.

## Commit Policy

Conventional Commits must always be used.

Use formats like:

- `feat: add the sign-in code confirmation`
- `fix: keep the timeline at the bottom after a resize`
- `docs: clarify packaging status`
- `ci: add Linux font dependencies`

Do not create non-conventional commit messages in this repository. The repository squash-merges pull requests, so the pull request title is the commit release-please reads.
